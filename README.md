# 空き状況モニター

予約サイトの空き状況を定期的に確認し、**「空きなし」→「空きあり」に変わったときだけ**
ntfy でスマホに通知する。空きが続く間は一定時間ごとに再通知し、空きが消えたら履歴をリセットする。

キャンプ場・駐車場・宿など**対象の種類は問わない**。サイトごとの読み取り方だけを
`adapters/` に足せば、取得・状態管理・通知・エラー処理は共通のものが使い回される。

## 役割分担

| 事象 | 通知経路 | 終了コード |
|---|---|---|
| **空きが出た**（本来の目的） | ntfy.sh の通知 | `0` |
| **監視が壊れた**（異常検知） | GitHub Actions のジョブ失敗メール | `1` |

通知したかどうかで終了コードは変わらない。`exit 1` は常に「監視が正しく動かなかった」を意味する。

## 構成

```
targets.yml       監視対象の一覧（ここを編集して対象を増やす）
monitor.py        共通ランナー。サイトに依存しない
discover.py       設定に書く項目を洗い出すツール
core/             取得・状態管理・通知・設定読み込み
adapters/
  ban489.py       489ban.net（予約番）系
  css.py          CSSセレクタで読む汎用アダプタ
  haneda_parking.py  羽田空港 第2・第3駐車場（JSON APIを直接叩く）
  haneda_p4p5.py  羽田空港 P4 / P5 駐車場（作りが同じなので1つで両対応）
  btimes.py       タイムズのB（btimes.jp）予約制駐車場
  _template.py    新しいシステムに対応するときの雛形
```

## 対象を増やす

### ① 対応済みシステムの別施設 → 設定だけ、コード変更なし

まず項目を洗い出す。

```bash
python3 discover.py --adapter ban489 --facility <施設名> --date 2026-09-19
```

```
見つかった対象: 76 件
  room_24246       空きなし   【F1】3家族サイト 大
  room_24247       空きなし   【F2】3家族サイト
  ...
targets.yml に貼る形:
    items:
      A1: room_24246          # 【F1】3家族サイト 大
```

出てきたものを `targets.yml` に貼る。

```yaml
targets:
  - id: akagi-family
    name: 赤城山オートキャンプ場 3家族サイト
    adapter: ban489
    date: 2026-09-19
    config:
      facility: autocamp-akagi
      items:
        F1: room_24246
        F2: room_24247
```

### ② 単純なページ（駐車場の満空など）→ 設定だけ、コード変更なし

「決まった場所に『空車』『満室』などの文字やclassが出る」型なら `css` アダプタで足りる。

```yaml
  - id: parking
    name: 〇〇駐車場
    adapter: css
    config:
      url: https://example.com/parking
      items:
        P1: { selector: "#lot-1 .status", name: 第1駐車場 }
        P2: { selector: "#lot-2 .status", name: 第2駐車場 }
      rules:                        # 上から順に、最初に一致したものを採用
        - { contains: 満車, status: full }
        - { contains: 空車, status: available }
        - { regex: '残り\s*[1-9]', status: available }
      default: closed               # 省略すると、一致しなかった時点でエラー
```

`contains`（テキスト） / `class` / `regex` で判定できる。
`url` に `{date}` を書くと日付が埋め込まれる。

### ③ 未対応のシステム → 関数を1つ書く

`adapters/_template.py` をコピーして `adapters/<名前>.py` にし、`parse()` を書く。

```python
def parse(html, config, date_str, warn=None):
    return {"F1": {"name": "サイトA", "status": st.AVAILABLE}}
```

**書くのはこれだけ。** 状態管理・再通知・通知文面・エラー処理は共通側が持つ。

判定できないときは必ず `MonitorError` を投げること。黙って「空きなし」を返すと、
サイトの変更に気づけないまま本当に空いたときに通知が飛ばなくなる。

## 使い方

```bash
pip install -r requirements.txt
export NTFY_TOPIC=your-secret-topic-name

python3 monitor.py                          # 全対象を確認
python3 monitor.py --list                   # 対象の一覧
python3 monitor.py --target akagi-family    # 1つだけ
python3 monitor.py --test-notify            # 通知を強制発火して疎通確認
```

### オプション

| オプション | 意味 |
|---|---|
| `--targets PATH` | 監視対象ファイル（既定 `targets.yml`） |
| `--target ID` | この id の対象だけ確認する |
| `--group NAME` | この group の対象だけ確認する（確認頻度の切り分け） |
| `--list` | 対象の一覧を表示して終了 |
| `--state PATH` | 状態ファイル（既定 `state.json`） |
| `--file PATH` | 実サイトの代わりにローカルHTMLを読む。既定では state を更新しない |
| `--test-notify` | 状態に関わらず通知を強制発火。state は更新しない |
| `--write-state-from-file` | `--file` でも state を更新する（テスト用） |

### targets.yml

| 項目 | 意味 |
|---|---|
| `id` | 対象の識別子。state の記録に使う（重複不可） |
| `name` | 通知に出る名前 |
| `adapter` | `adapters/` のモジュール名 |
| `date` | 監視対象日。日付の概念がない対象（駐車場など）は省略可 |
| `enabled` | `false` にすると一括実行から外れる |
| `group` | 確認頻度のグループ。`normal`(30分) / `fast`(10分)。既定は `normal` |
| `repeat_hours` | 空きが続く間の再通知間隔（既定は `defaults.repeat_hours`、2時間） |
| `min_available` | 同じ枠で何日以上空いたら通知するか（既定 `1`。下記） |
| `priority_dates` | この日だけは1日でも通知する（`min_available` の例外） |
| `config` | アダプタに渡す設定 |

### 終了コード

`exit 1` になるのは次の場合。**該当した対象の state は更新されない。**

- `NTFY_TOPIC` が未設定（起動直後に判定）
- `targets.yml` の不備（id重複、adapter無し、未知のadapter など）
- ページ取得に失敗した（4回まで指数バックオフで再試行したうえで失敗）
- 設定した項目がページ内に見つからなかった
- 状態を判定できなかった
- ntfy.sh への送信に失敗した

複数対象のうち1つが失敗しても、**残りの対象の確認は続行される**。
失敗した対象だけ state が据え置かれ、全体としては `exit 1` になる。

## 通知の仕様

**新規通知** — 「空きあり以外」→「空きあり」に変化したとき。

```
赤城山オートキャンプ場 3家族サイト 空き通知

2026-09-19 に空きが出ました。

・F2  【F2】3家族サイト

予約ページ:
https://reserve.489ban.net/...
```

**継続通知** — 空きあり状態のまま、最終通知から2時間経過したとき。

```
赤城山オートキャンプ場 3家族サイト 空き継続中

【継続中】2026-09-19 は引き続き空きがあります。

・F2  【F2】3家族サイト（継続中）

※ 空きが続く間は 2 時間ごとにお知らせします。
```

対象ごと・項目ごとに判定するため、F2だけ2時間経過していれば F2 だけが載る。
空きが消えた項目は履歴がリセットされ、次に空いたときは「新規」として通知される。

**テスト通知** — `--test-notify` のとき。本物と見分けられるよう文面を変え、
「空きが出ました」とは書かずに、その時点の実際の判定結果をそのまま載せる。

```
【テスト】赤城山オートキャンプ場 3家族サイト 監視テスト

これは通知テストです。空きが出たという意味ではありません。

対象: 赤城山オートキャンプ場 3家族サイト

現在の判定結果（2026-09-19）:
・F1  空きなし  【F1】3家族サイト 大
・F2  空きなし  【F2】3家族サイト
```

### min_available（まとまった空きだけ通知する）

「1日だけ空いても意味がない」対象向け。`min_available: 3` にすると、
**同じ枠の中で** 空きが3日以上あるときだけ通知する。

```yaml
  - id: haneda-p4
    min_available: 3          # 8/22〜25 のうち3日以上空いたら通知
    config:
      dates: [2026-08-22, 2026-08-23, 2026-08-24, 2026-08-25]
```

「同じ枠」はアダプタが `series` として返す単位。羽田なら駐車場×種別
（P4の一般、P4の個室、P2、P3 …）。**別々の駐車場に1日ずつ空いても通知しない** —
車は1か所にしか停められないため。

条件を満たすと、その枠で空いている日が**まとめて**通知される。
条件を下回ると通知履歴がリセットされ、再び満たしたときにまた全部通知される。

**特定の日だけは1日でも知りたい**場合は `priority_dates` に入れる。

```yaml
    min_available: 3               # ふだんは3日まとまったときだけ
    priority_dates: [2026-08-22]   # ただし 8/22 は単独でも通知
```

対象を分けて二重に監視するのではなく1回の取得で両方を判定するので、
サイトへのアクセスは増えず、両方に該当しても通知は1通にまとまる。

## state.json

**正常にパースできて、通知も成功したときだけ書き込む。** 取得失敗・構造変化・
通知送信失敗の場合は書き込まないため、失敗を「空きなし」と誤記録して次回に
誤通知することがない。通知送信に失敗した回は履歴を更新しないので、次回やり直す。

```json
{
  "targets": {
    "akagi-family": {
      "updated_at": "2026-08-04T12:00:00+09:00",
      "date": "2026-09-19",
      "items": {
        "F1": { "status": "full",      "name": "【F1】3家族サイト 大", "notified_at": null },
        "F2": { "status": "available", "name": "【F2】3家族サイト",     "notified_at": "2026-08-04T12:00:00+09:00" }
      }
    }
  }
}
```

`notified_at` が再通知の制御に使われる。空きあり以外の項目は常に `null`（＝履歴リセット）。

## 状態の語彙

アダプタはこの語彙に正規化して返す。通知の対象になるのは `available` だけ。

| 値 | 表示 |
|---|---|
| `available` | 空きあり ← 通知対象 |
| `full` | 空きなし |
| `phone` | 要問い合わせ |
| `closed` | 受付不可 |
| `unknown` | 不明 |

## ban489 アダプタの判定ロジック

| 対象 | 方法 |
|---|---|
| 区画の特定 | `li[id="room_24246"]`（`config.items` で指定） |
| 名称 | `li` 内の `dl.webc_avlbl_item dt` |
| 日付列 | 先頭列の日付を基準に「何日後か」で列を求める（下記） |
| 空き状況 | 同じインデックスの `tbody td` 内の `<i>` の class |

| class | 判定 |
|---|---|
| `fa-circle` | 空きあり |
| `fa-xmark` | 空きなし |
| `fa-square-phone` | 要問い合わせ |
| `fa-minus` | 受付不可 |

補助チェックとして「空きありの td のみリンクを持つ」も検査し、食い違ったら警告を出す
（判定自体は `<i>` の class を優先）。

### 日付列の求め方

**月付きの日付表記は先頭列にしか無い。** 実サイトのHTMLで確認済み:

```html
<!-- th[0] -->  <span>9/19</span><span>土</span>
<!-- th[1] -->  <span>20</span><span>日</span>      ← "9/20" ではない
<!-- th[12] --> <span>1</span><span>木</span>        ← 10/1 だが "10/1" ではない
```

そのため「`9/19` に一致する列を探す」方式では**先頭列しか引けない**。
先頭列の `M/D` を基準日として読み（年は表記に無いので監視対象日に最も近い年を採用）、
**目的日との日数差を列インデックスにする**。そのうえで、求めた列のラベルが
本当に目的の日かを検証してから読む:

- 日付が食い違う → `exit 1`（列の増減など構造変化の可能性）
- 曜日が食い違う → 警告のみ（判定は続行）
- 日数差が表示範囲外 → `exit 1`

## GitHub Actions での定期実行

確認頻度ごとにワークフローを分けてある。どちらで回すかは `targets.yml` の `group` で決まるので、
**対象を増やすときにワークフローを触る必要はない。**

| ワークフロー | 確認のしかた | group | 状態ファイル |
|---|---|---|---|
| [`akagi.yml`](.github/workflows/akagi.yml) | 起動ごとに1回（30分ごと起動） | `normal` | `state.json` |
| [`haneda.yml`](.github/workflows/haneda.yml) | **起動ごとに55分間・3分おき** | `fast` | `state-fast.json` |

### スケジュールに頼らない理由（実測）

GitHubのスケジュール実行は best-effort で、指定どおりには動かない。
`*/10`（10分ごと）で18時間動かした実測:

| | |
|---|---|
| 本来の回数 | 108回 |
| 実際の回数 | **30回** |
| 間隔の中央値 | **32分** |
| 最長の間隔 | **144分** |
| 10分±1分だった回数 | **0回** |

cronを `*/5` に変えても、詰まっているのはGitHub側なので改善しない。
そこで `fast` は**起動の粒度に頼らず、1回の起動の中で繰り返し確認する**
（`--loop-minutes 55 --interval-seconds 180`）。
`concurrency` により実行中に来た起動は待機し、終了と同時に始まるので、
起動が30分間隔で来ている時間帯はほぼ切れ目なく監視できる。
publicリポジトリのため実行時間の費用はかからない。

ループ長は実測した起動12回でシミュレーションして決めた:

| ループ長 | 監視できる割合 | 見ていない時間の合計 | 空白の回数 | 確認回数 |
|---|---|---|---|---|
| 25分 | 51% | 290分 | 10回 | 10.9回/時 |
| **55分** | **71%** | **182分** | **4回** | **14.4回/時** |

**ただし完全ではない。** GitHubが1〜2時間まったく起動しないことが実測で確認されており
（09:00→11:23 の143分など）、その空白はループ長を変えても埋まらない。
切れ目のない監視が必要なら、外部から `repository_dispatch` を叩くなど
GitHubのスケジューラに依存しない起動手段が要る。

ループ中に一時的な取得失敗があっても、最後の回で復旧していればジョブは失敗させない
（一過性の不調で「監視が壊れた」メールを飛ばさないため）。最後まで失敗していれば `exit 1`。

`fast` は空きが数分で消える対象向け。羽田の駐車場は実測で
**16:48に混雑だった枠が17:02には満車**になっていたため、30分間隔では取り逃す。

状態ファイルを分けているのは、10分ごとと30分ごとが同じファイルを
押し合ってコミットが衝突するのを避けるため。

なお `monitor.py` は**中身が変わったときしか state を書かない**ので、
10分ごとに回しても変化が無い限りコミットは増えない。

### 設定手順（ブラウザだけで完結）

1. **トピック名を決める** — 名前を知っていれば誰でも購読できるので推測されない文字列にする
2. **スマホに ntfy アプリを入れ**、そのトピック名を購読する
3. GitHubの **Settings → Secrets and variables → Actions → New repository secret** で
   Name に `NTFY_TOPIC`、Secret にトピック名を登録
4. **Actions タブ → akagi-monitor → Run workflow** で
   `通知テスト` に **✓** を入れて実行 → スマホに通知が届けば設定完了

`if: always()` を付けてよい理由: 正常にパースできた対象しか state を書かないので、
異常終了した回に誤った状態がコミットされることはない。

ジョブが失敗（`exit 1`）したら GitHub からメールが届く。
これは「空きが出た」ではなく「**監視が壊れた**」の合図なので、ログを確認すること。
